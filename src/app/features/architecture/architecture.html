Architecture

What this console drives: an event-driven order processing system, ported from an Azure/Service Bus original to AWS. ASP.NET Core for the API, .NET 8 Lambdas, SQS FIFO queues, an SNS FIFO topic, and SQL Server.

info Mirrors TradingApp-AWS/README.md, which is the current source of truth for the AWS port. Update the README first, then this page.

Where things actually run

Only SQS and SNS are real cloud resources. SQL Server runs locally, and the day-to-day workflow runs each Lambda locally through its own harness against those real queues. There is no CloudFormation, SAM or CDK stack — queues, the topic, subscriptions, redrive policies and the ReportBatchItemFailures flag on each event source mapping are all provisioned by hand through the AWS console or CLI.

Local development harnesses

Every Lambda has a paired *.LocalHarness console app, so it runs and debugs locally against the real cloud SQS/SNS resources and a local SQL Server. A full cloud deploy is only needed to verify the deployed artifact, never for routine work.

  • SqsHarness.RunAsync — for the five SQS-triggered Lambdas. Polls the real queue, converts each message to an SQSEvent, invokes the handler, and deletes on success or leaves it for real SQS retry semantics on failure.
  • ScheduledHarness.RunAsync — for the three scheduler-triggered Lambdas. A deliberately simpler loop: call the handler, log, wait a minute.

Each harness builds its DI container from the same Startup.ConfigureServices the deployed Lambda uses and resolves the real class, so it never duplicates a Lambda's constructor shape or registrations.
